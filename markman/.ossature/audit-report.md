# Audit Report: markman v0.0.1

**Date:** 2026-03-14T11:22:44Z
**Specs:** STORAGE, CLI, WEBUI

## Cross-Spec Findings

No cross-spec findings identified.

## STORAGE Findings

### WARNING: Search Bookmarks, Returns

**Issue:** The spec shows created_at in the example output as 'T' separated ISO format ('2026-01-01T00:00:00'), but the requirement explicitly states it is stored and returned as 'YYYY-MM-DD HH:MM:SS' format (space-separated, as produced by SQLite `datetime('now')`). This ambiguity could cause implementations to differ in timestamp format returned to callers.

**Suggestion:** Either clarify that created_at is returned in space-separated format (e.g., '2026-01-01 00:00:00') matching SQLite's datetime() output, or update the example to match the spec requirement. Recommend removing the 'T' from the example output.

### INFO: Constraints, Schema

**Issue:** The schema specifies `DEFAULT (datetime('now'))` for created_at, but there is no explicit statement about what happens if a caller provides their own created_at value during insert. The spec does not list created_at as an accepted parameter for Add Bookmark, implying it is always server-generated, but this could be clarified.

**Suggestion:** Consider adding a note that created_at is always auto-generated by the database and cannot be specified by the caller, or explicitly state that the Add Bookmark function only accepts conn, url, desc, and tags.

## CLI Findings

### WARNING: Requirements > list subcommand, Errors

**Issue:** The spec states that search filtering is performed via a 'query' argument, but does not define what fields are searched (URL, description, tags, all of them?) or what matching logic is used (substring, regex, exact match?). Two implementations could reasonably differ in search behavior and produce incompatible results.

**Suggestion:** Clarify the search scope ('query matches URL, description, and tags') and the matching algorithm ('case-insensitive substring matching').

### WARNING: Requirements > remove subcommand, Errors

**Issue:** The spec requires printing 'error: id must be a positive integer' for 'missing or non-integer id', but does not explicitly state that id must be *positive* (>0) as a constraint. An implementation could accept 0 or negative integers without violating the non-integer check, creating incompatible behavior.

**Suggestion:** Clarify: should id validation reject zero and negative integers? If so, update the error message to reflect range validation, or define the valid id range explicitly.

### INFO: Requirements > list subcommand, Returns

**Issue:** The output format includes 'tags: <tags>' but it is unclear whether empty tags should display as 'tags: ' (with no tag values) or be omitted entirely. The example shows a bookmark with tags, but no example of a bookmark without tags.

**Suggestion:** Add an example showing a bookmark with no tags to clarify the output format (e.g., does '[1] https://example.com | Example site | tags: ' or '[1] https://example.com | Example site' appear?).
